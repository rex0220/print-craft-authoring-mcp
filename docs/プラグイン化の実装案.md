## 1. 目的

| 今の課題 | 目指すこと |
| --- | --- |

## 2. 全体の構成

```
print-craft-authoring（既存。公開、MIT）
  テンプレート              ← CLAUDE.md、.claude/settings.json、.mcp.json（kintone MCP）、policy/、environments.example.json
  tools/ の中核             ← 共通の中核（npm @rex0220/print-craft-authoring-tools の入口 /core。2026-10-09 Takashi「B」。別のパッケージにしない）
  tools/ の CLI             ← 今の CLI（同じパッケージ。中核と版は 1 つ）

print-craft-authoring-mcp（新規。公開、MIT。12.4）
  src/                      ← print-craft MCP。core を束ねた 1 つのファイルにビルドする（8.3）
                               起動の引数 --surface claude-code | desktop で、出すツールを分ける（5.1）
  mcpb/                     ← .mcpb（Desktop のチャット用）。manifest は package.json から作る
  .claude-plugin/ skills/ hooks/  ← Claude Code のプラグイン print-craft（スキル、フック、.mcp.json で同じビルドを起動）
  compat.json               ← 互換表（7 章）
```

役割の分け方:

- **print-craft MCP** — 処理の本体と**強制の境界**。書く先、本番の読み取り専用、ダウンロードのファイルの不変、kintone に書かない、秘密の値を返さない、をサーバーの中で守らせる。Desktop のチャットではフックが動かないので、ここだけが境界になる
- **スキル / 資料のツール** — 知識と手順（案内）。読まれないと効かないので、守らないと壊れる制約は置かない（置いてもよいが、print-craft MCP か CLAUDE.md にも置く）
- **フック** — Claude Code（と Cowork）だけ。print-craft MCP の外の呼び出し（Read、Bash、Write、Edit）への補助の制約と、作業フォルダーの結び付け（4.1）。失敗しても拒否になるように書く
- **テンプレート** — 作業フォルダーの形、policy、git の運用。プラグインを入れない利用者（今の CLI の使い方）のための今の手順

## 4. フック（Claude Code。`hooks/register.ts`）

フックは Claude Code と Cowork でだけ動く（チャットでは無視される。13.2 の表）。

| フック | 内容 | 今の扱い |
| --- | --- | --- |
| `tool.call`（print-craft MCP の、作業フォルダーを使うツール。5.1） | 4.1 の手順で、ツールの入力の `workspaceId` を、今のセッションのフォルダーに合う登録済みの作業フォルダーの実際のパスに**書き換える**（AI が渡した値は使わない。型定義では MCP のツールの引数は `e` の直下にあり、`next({ ...e, workspaceId })` で書き換えられる）。合わなければ登録の確認（4.1）か拒否。作業フォルダーを使わないツール（`pcraft_docs`、診断）には何もしない | なし |
| `tool.call`（Write / Edit） | **`kintone/` の下と `settings/**/*.json` への直接の Write / Edit を拒否する**（2026-10-09 Takashi 決定。プラグインを使う人だけ）。パスの判定は 4.2。理由に「print-craft MCP の保存のツールを使う」と返す。組み込みの Write / Edit は print-craft MCP を通らないので、ここを止めるのはこのフックだけ。テンプレートの `.claude/settings.json` は今の使い方のために変えない | `.claude/settings.json` は `Write(kintone/**)` を許可 |
| `tool.call`（Read / Bash / PowerShell） | 既存の設定ファイル（`settings/**/*.json`、`kintone/**/*.json`）を Read、`cat`、`head`、`Get-Content`、`node -e` で丸ごと表示しようとしたら拒否。理由に「`pcraft_buttons` を使う」と返す | CLAUDE.md の文章 |
| `tool.call`（Bash / PowerShell） | `open`、`start`、`chrome`、`--headless` などのブラウザーの起動を拒否 | CLAUDE.md の文章 |
| `tool.call`（Bash / PowerShell） | `KINTONE_PASSWORD` などの秘密の変数名を含むコマンドを拒否（補助。秘密を Bash に渡さないのが本来の対策。6.2） | なし |
| `session.start` | 互換表（7 章）と印刷屋の zip の場所の確認。足りなければ `$.ui.toast` で知らせる | 実行して初めて分かる |

- **失敗しても拒否にする（fail-closed）。** 付属資料では、例外・時間切れ・不正な返り値のフックは飛ばされて次へ進む（`reference.md` 74 行目）。拒否のフックには必ず `.catch(($, e, next) => next.called ? next(e) : { deny: "…" })` を付け（型定義と一致することを 3 回目のレビューで確認）、例外・時間切れ・入れ直しでも拒否になることを `claude plugin test` で試す
- **Bash の文字列の検査は境界にしない。** 別のコマンド、変数の展開、スクリプトファイルで抜けられる。設定の読み書きは print-craft MCP に寄せ、サーバーで強制する。ツール名は `String(e.tool)` で比べ、版や OS で増えるツール（PowerShell など）も対象にする
- 書いた後の normalize の自動実行（後置のフック）はしない（Edit の途中の状態を検査・書き戻してしまう）。保存と normalize は print-craft MCP で 1 回に行う（5.3）
- `.claude/settings.json` の拒否の規則（kintone MCP の書き込みツール、`policy/` など）はそのまま残し、フックと二重にする
- `role`（13.3）による判断はサーバーだけに置く。`.claude/settings.json` の静的なパスの規則には期待しない

### 4.1 作業フォルダーの決め方

2026-10-09 Takashi 決定（Desktop は起動時に固定、Claude Code は `workspaceId` とフックの照合）。

**Desktop（`.mcpb`。`--surface desktop`）**

- 設定項目 `workspaceDir`（`user_config` の `type: "directory"`、必須）を起動の引数で受け取る
- 起動時に「絶対パスか」「存在するか」「フォルダーか」を確かめ、実際のパス（realpath）に直して固定する。だめなら起動のエラー（標準エラー）にして、ツールは `denied` を返す。kSQL は仕様で同じ確かめを決めていたがコードで行っていなかった（設定ファイルが無いと黙って空の設定で動いた）ので、ここは試験で確かめる
- **起動時の作業フォルダー（`cwd`）は使わない**（kSQL: Desktop では `C:\WINDOWS\system32` などになる）
- **設定項目の値は、前後の空白と両端の `"` / `'` を外し、パスの先頭の `~/` はホームのフォルダーにしてから使う**（`~` は試作 0-3b: 設定の欄はシェルを通らないので展開されず、`~/…` を入れて「絶対パスでない」になった。`~user` の形は展開しない）（作業フォルダー、zip、URL。試作 0-4 の Windows で、エクスプローラーの「パスのコピー」の `"C:\…"` の形を貼ると「絶対パスでない」になった。今の `.env` の `PCRAFT_PLUGIN_ZIP` も `"` 付きのまま読める）
- **作業フォルダーが無ければ作る**（2026-10-09 Takashi。試作 0-4 で、Desktop の「フォルダー」の設定項目は存在しないパスも受け付けて渡すと分かった）: 絶対パスで、すぐ上のフォルダーが存在してフォルダーのときだけ、最後の 1 段だけを作る（打ち間違いで深いところまで作らない）。同じ名前のファイルがあれば使わない。作ったことを `pcraft_status` / `pcraft_workspace_status` に出す
- 起動時にだめなら、作業フォルダーを使う呼び出しのたびに同じ設定の値で確かめ直す（値は AI の引数で変えられないまま。拡張機能の入れ直しや再起動を求めない）
- **Desktop はサーバーを何度も起動し直す**（試作 0-4: 更新のとき 0.1 秒ほどの間に 4 回）。起動の処理は何度走っても同じ結果になるように書き、プロセスごとの印（「この起動で作った」など）を答えに出さない（AI が `created: false` を「作られていない」と読み違えた）。作ったことを伝えるなら、作業フォルダーの中の印（例 `.print-craft/workspace.json` に作った日時と版）か、標準エラーの行（Desktop は `main.log` に残す）にする
- ツールの `workspaceId` は省略できる。渡されて固定のフォルダーと違えば `denied`

**Claude Code（プラグイン。`--surface claude-code`）**

1. プラグインの `.mcp.json` が、登録済みの作業フォルダー（`userConfig` の `workspaceRoots`）を起動の引数で print-craft MCP に渡す（配列の渡し方は 0-3a で確かめる。だめなら JSON の文字列 1 つ）。サーバーは起動時にすべてを実際のパスに直し、絶対パスでない・存在しないものを捨てる
2. print-craft MCP の作業フォルダーを使うツール（5.1）は `workspaceId`（登録済みの作業フォルダーの実際のパス）を必須にする。サーバーは登録済みのものと一致しなければ `denied`
3. プラグインのフック（4 章の表の 1 行目）が、呼ばれるたびに次を行い、`workspaceId` を書き換える
   1. `await $.session.root()` でセッションのフォルダーを取る（`/cd` や worktree で変わりうるので、毎回取る）
   2. 登録したフォルダーとセッションのフォルダーを、どちらも `$.fs.stat(…, { resolve: true })` で実際のパスに直す（symlink を解く。Windows は大文字小文字をそろえて比べる）
   3. 「セッションのフォルダーが登録したフォルダーと同じか、その中」のものが **1 つだけ**合えば、その実際のパスを `workspaceId` にする
   4. 合わない・2 つ以上に合う・解決できないときは、認証情報を使う前に拒否するか、下の登録の確認を出す
4. フックが失敗しても `.catch` で拒否になる。仮にフックを通らなくても、サーバーは登録済みのフォルダーしか受け付けない（最悪でも AI が登録済みの別のフォルダーを選ぶだけ）

**登録のしかた**（2026-10-09 Takashi 決定。`/config` に手でパスを書いてもらう形にはしない）

| 画面 | 登録のしかた |
| --- | --- |
| Desktop の `.mcpb` | インストールの画面のフォルダーを選ぶ画面で選ぶ（`workspaceDir`）。これが登録で、追加の手間は無い |
| Claude Code のプラグイン | 登録されていないフォルダーで初めて print-craft MCP を呼んだとき、フックが利用者に「このフォルダーを印刷屋の作業フォルダーとして登録しますか」と聞く（`$.ui.ask`） |

Claude Code の登録の細かい決まり:

- 聞くのは利用者本人への確認の画面で、AI は答えられない（改変されたフォルダーを AI が勝手に信頼しない）。`$.ui.ask` は headless（`claude -p`）では拒否されるので、そのときは拒否にする
- 「はい」なら `$.config.list()` で実際のキー（`print-craft.workspaceRoots`）を確かめて `$.config.set` で足す（型定義でプラグインの `userConfig` を変えられ、配列も値にできることを 3 回目のレビューで確認）。`{ deny }`、取り消し、headless は拒否として扱う
- 設定を変えるとプラグイン（フック）は新しい設定で読み込み直される（`reference.md` 70 行目）が、**print-craft MCP は起動し直さない**（試作 0-3a で確かめた。`/mcp` の再接続か Claude Code の起動し直しで新しい値が届く）。プラグインの API に MCP サーバーを起動し直す手段は無く（`$.mcp.connect` はつながっているサーバーにはそのまま答える）、`$.command.run` はツールの呼び出しのフックの中では拒否される
- **登録の後は、利用者に再接続してもらう**（2026-10-09 Takashi。登録は作業フォルダーごとに最初の 1 回だけなので、そのときだけの手間にする）。同じ呼び出しは続けず「作業フォルダーを登録しました。`/mcp` で print-craft を再接続（Reconnect）するか、Claude Code を起動し直してから、もう一度実行してください」と返す
- 再接続を忘れたとき: フックでは登録済みなのに、サーバーが「登録済みの作業フォルダーでない」と断ったら、サーバーが古い設定のまま動いている。フックがサーバーの答えを見て、同じ再接続の案内に置き換える（AI と利用者が「登録したのに断られた」と迷わないように）
- 設定項目は**文字列 1 つに JSON の配列**（`["/Users/…"]`）。文字列の配列（`"multiple": true`）は validate を通るが `/config` の行にならない（試作 0-3a）
- 確認の画面は分かりやすくする（試作 0-3a で「登録する」が灰色で押せないように見え、取り違えた）: 項目に説明を付ける、先頭を「登録する（おすすめ）」にするなど
- 登録したフォルダーは `/config` で確かめ、外せる。`$.config.set` が使えず `$.store` に保存する場合は `/config` に出ないので、一覧・削除のコマンド（`/print-craft:folders`）を作る

### 4.2 直接の Write / Edit を拒否するときのパスの判定

今の `tools/src/safe-path.ts`（存在する一番深い親を realpath に直す、Windows は小文字にそろえる、区切りを含めて親子を比べる）と同じ規則をフックでも使う。

1. Write / Edit の `file_path` を、セッションのフォルダーを起点に絶対パスにする
2. 存在する一番深い親を `$.fs.stat(…, { resolve: true })` で実際のパスに直し、残りをつなげる（symlink / junction を解く。Windows は大文字小文字・UNC・ドライブをそろえる）
3. **登録の状態と関係なく**判定する（Claude Code の登録は初めて print-craft MCP を呼んだときなので、その前の Write / Edit も止めるため）。起点のフォルダーは次のとおり
   - セッションのフォルダー（`$.session.root()` を実際のパスに直したもの）の祖先か同じに、登録済みの作業フォルダー（4.1）が 1 つだけあれば、その作業フォルダー
   - 無ければ、セッションのフォルダー
4. 起点のフォルダーの中なら、そこからの相対パスを出し、`kintone/**` か `settings/**/*.json` なら拒否する。起点のフォルダーの外のパスは、このフックでは止めない（印刷屋と関係のないファイル）
5. 解決できない、リンクが切れている、起点のフォルダーが 1 つに決まらない、のどれかなら拒否する
6. 0-3a で、絶対パス、`settings/../kintone/…`、symlink、junction、Windows の大文字小文字、**プラグインを入れた直後で `workspaceRoots` が空・print-craft MCP を一度も呼んでいない状態**を試験する（9 章）

### 5.1 ツールの一覧

| ツール | 中身 | 作業フォルダー | Claude Code | Desktop |
| --- | --- | --- | --- | --- |
| `pcraft_docs` | 手順と資料（5.5）。引数なしで目次（版を含む）、`section` でその章 | 使わない | 出す | 出す |
| `pcraft_status` | 作業フォルダーに依存しない診断（サーバーの版、互換表の判定、設定項目のそろい具合。秘密の値は出さない） | 使わない | 出す | 出す |
| `pcraft_workspace_status` | 作業フォルダーの診断（登録済みか、`environments.json` の有無、環境ごとの `role` と未分類の環境。13.3） | 使う（互換表の判定は通さない） | 出す | 出す |
| `pcraft_save_settings` | **新しい設定**を保存する（5.3） | 使う | 出す | 出す |
| `pcraft_update_button` | **既存の設定**のボタンを 1 つ差し替える・足す（5.3） | 使う | 出す | 出す |
| `pcraft_normalize` | normalize を実行し、エラー・警告・情報を返す（`--check` / `--dry-run` 相当） | 使う | 出す | 出す |
| `pcraft_preview` | preview を実行し、出したファイルとページ数・式のエラーを返す | 使う | 出す | 出す |
| `pcraft_buttons` | ボタンの一覧と中身（data: の URL は先頭と長さだけ）、ファイル全体の digest、ボタンの識別子（`menu`） | 使う | 出す | 出す |
| `pcraft_fields` | 項目定義を作業フォルダーに保存し、要約（1 項目 1 行）を返す | 使う | 出す | 出す |
| `pcraft_record` | レコード 1 件を作業フォルダーに保存し（preview 用）、形の要約だけを返す（値は返さない。今の `record --summary`） | 使う | 出す | 出す |
| `kintone_get_app` | アプリ 1 件の情報（`app` の API）。アプリの番号か URL から（5.4） | 使う | 出さない（kintone MCP） | 出す |
| `kintone_list_records` | レコードを数件、**形の要約だけ**（5.4）。代表の 1 件を選ぶため | 使う | 出さない（kintone MCP） | 出す |
| `pcraft_files` / `pcraft_take` / `pcraft_edit` / `pcraft_pull` / `pcraft_diff` | 今の `files`、`take`、`edit`、`pull`、`diff`（B1 で足す。最初の試作には要らない） | 使う | 出す | 出す |

- ツールは 3 種類に分ける。① **作業フォルダーを使うツール**は `workspaceId` を入力に持ち、作業フォルダーの照合（4.1）と互換表の判定（7 章）を通す。② **作業フォルダーを使わないツール**（`pcraft_docs`、`pcraft_status`）は `workspaceId` を持たず（`additionalProperties: false` のため、フックも書き換えない）、照合と互換表の判定の対象外。③ **作業フォルダーの診断**（`pcraft_workspace_status`）は `workspaceId` を持ち照合は通すが、互換表の判定は通さない。登録の前や版が合わないときにも、目次・版・導入の手順・診断を読めるようにするため

- **出し分け**は起動の引数 `--surface claude-code | desktop` で決める。引数はプラグインの `.mcp.json` と `.mcpb` の manifest に固定で書き、AI の引数では変えない（kSQL の B91 でも「AI は引数を渡し忘れる」ので起動の設定で決める案が出た）。公式の kintone MCP と同じことをするツールを Claude Code で出さない（「両方を出して AI に選ばせる」はしない）
- 担当の分け方: **AI に値を直接返す GET** は Claude Code では kintone MCP、Desktop では `kintone_get_app`（値はアプリの情報だけ）。**作業フォルダーに保存して要約だけ返す処理**（`pcraft_fields`、`pcraft_record`）はどちらも print-craft MCP
- **処理はサーバーの中で共通の中核を呼ぶ**（別のプロセスを起動しない）。印刷屋の zip のコードも同じプロセスで動く（受け入れた危険。13.4）
- **引数** — ファイルは作業フォルダーからの相対パスだけ。`..`、絶対パス、ドライブ名、`cwd` を受け付けない
- AI から見えるツールの名前は、Claude Code ではプラグインの MCP サーバーの名前が付く（形は 0-3a で確かめる）。許可の規則をプラグインから配れるか（プラグインの `settings`）も 0-3a で確かめる。配れなければ、利用者がツールごとに許可を確かめる形のままにする（テンプレートの `.claude/settings.json` には足さない。11 章の決定）
- 読み取りだけのツール（`pcraft_docs`、`pcraft_buttons`、`kintone_*` など）には `annotations: { readOnlyHint: true, openWorldHint: false }` を付ける

### 5.2 入出力の約束（全ツール共通）

kSQL の形（`ksql_mcp_server_spec.md`、`tools.ts` の `toToolResult`）にそろえる。段階 0 の関門で 1 つのツールについて完全に決め、0-3b で試す。

- **入力** — `inputSchema` は `additionalProperties: false`。`content` / `replacement` は 256 KB まで（印刷屋の保存値の上限に合わせる）
- **応答** — `content: [{ type: "text", text: <JSON> }]` と、同じ内容の `structuredContent`、失敗なら `isError: true`。`pcraft_docs` だけは文章のみ

  ```json
  { "ok": true, "status": "ok", "findings": [{ "level": "warning", "rule": "…", "message": "…", "where": "…" }], "result": { … }, "digest": "…" }
  { "ok": false, "status": "invalid" | "incompatible" | "conflict" | "denied" | "failed", "error": { "code": "…", "message": "…" }, "findings": [ … ] }
  ```

  `invalid` は normalize のエラー、`incompatible` は互換表に合わない（7 章）、`conflict` は digest が違う・ファイルがある、`denied` は本番・ダウンロードのファイル・作業フォルダーの外・未登録の `workspaceId`、`failed` は時間切れ・上限・想定外の失敗。打ち切ったときは `findings` に `truncated` を出す
- **出さないもの** — 認証情報、接続先の URL の認証部分、kintone のサーバーの message（今の tools と同じく、HTTP の状態と kintone のエラーコードと固定のヒントだけ）
- **AI が読み違えない形にする**（試作 0-4 の 5d）。状態を返すツール（`pcraft_status`、`pcraft_workspace_status`）は、値に加えて「準備ができている / 何が足りないか（次にすること）」を文章でも返す。値の名前は意味がはっきりしたものにする（`exists`、`configured` など。「この起動で作ったか」のような、読み違えやすい印を出さない）
- **結果を推し量らせない**（試作 0-3b）: Desktop の AI は、直前に保存した・ツールの説明に書ける場所がある、から結果を推し量り、ツールを呼ばずに「保存できませんでした」と答えた（「必ず呼んで、返った結果をそのまま」と頼むと呼んだ）。保存・更新のツールの説明、`instructions`、`pcraft_docs` の目次に「保存できるか・結果を推し量らない。必ずツールを呼び、返った `status` をそのまま伝える」と書く。説明に書ける場所や断る場合を詳しく書くほど推し量りの材料になるので、説明は「何をするか」にとどめ、断る場合の一覧は `pcraft_docs` に置く
- **標準出力は JSON-RPC だけ**。途中の表示は標準エラー（Desktop は `main.log` に `[UtilityProcess stderr]` として残す。拡張機能のログは手順だけ。試作 0-3b）

### 5.3 保存の約束

- **新しい設定**（`pcraft_save_settings`）: `{ workspaceId, path, content, fields?, expectedAbsent: true }`。同じ名前のファイルがあれば `conflict`。既存のファイルの上書きはこのツールでしない
- **既存の設定**（`pcraft_update_button`）: `{ workspaceId, path, button（menu の名前）, expectedDigest, replacement, fields? }`。`pcraft_buttons` が返した digest を渡す。保存の直前に digest を取り直し、違えば `conflict`。ボタンは `menu` の名前で選ぶ（設定の中で一意。normalize の `menu.duplicate`）
- **確定の仕方**: normalize（`fields` は、アプリのフォルダーなら同じフォルダーの `fields.json`、それ以外は引数の `fields` を必須） → エラー 0 のときだけ、書く先のパス・本番（`environments.json` を読み直す）・ダウンロードのファイルを確かめてから、確定先と同じフォルダーに一時ファイルを作る（normalize の間に本番に変わったフォルダーには何も作らない） → 確定先のロック（隣の `.<名前>.pcraft-lock` に所有者の印。60 秒より古いものは回収する。外すのは自分のロックだけ）を取る → 書く先のパス（symlink / junction の差し替え）・本番・ダウンロードのファイル・digest・ロックがまだ自分のものかをもう一度確かめて確定する。新しい設定はハードリンクで確定し（同じ名前があれば失敗する = 確かめた後に作られたファイルも上書きしない）、既存の設定は名前の付け替えで確定する。アプリのフォルダーで別の `fields` を渡されたら拒否する。`content` / `replacement` は UTF-8 で 256 KiB まで。失敗・中断のときは元のファイルを残し、一時ファイルとロックを消す。確定の後に片付けられなかったときは、確定の失敗にせず結果に添える（0-2 の Codex レビュー 3 回で決めた。tools の `src/commands/save.ts`、`src/commit-file.ts`）
- **警告**は確定を止めない。`findings` で返し、AI が利用者に伝える（今の CLAUDE.md と同じ）

### 5.4 kintone の GET（Desktop。6.3）

- **アプリの名前検索はしない。** 「複数のアプリの情報を取得する」（`apps.json`）の認証はパスワード認証・セッション認証・OAuth 認証だけで、**API トークンは使えない**（kintone の公式の資料で確認。kSQL の B49 も同じ理由で外した）。一般の利用者には閲覧専用の API トークンを勧めるので、アプリの番号か URL を利用者に入れてもらう
- **`kintone_get_app`** の入力は `{ workspaceId, app }`（`app` は番号か URL）
  - 番号は正の安全な整数だけ
  - URL は https で、**オリジンが設定項目の接続先（`kintoneBaseUrl`）と一致するときだけ**受け付ける（別の環境の URL から番号だけを抜いて、設定済みの環境の同じ番号を取らない）。形は `/k/<番号>/` とゲストスペースの `/k/guest/<スペース>/<番号>/` だけ。ユーザー名・パスワードの部分があれば拒否し、query と fragment は無視する
  - 応答は**決めた項目だけ**を返す: `appId`、`name`、`code`、`spaceId`、`threadId`。作成者・更新者（コードと氏名）と説明の全文は返さない（「1 件のアプリの情報を取得する」の応答には作成者・更新者が入る）。文字列の長さと応答全体に上限を付ける
- **`kintone_list_records`** は値を返さない。入力は `{ workspaceId, app, guestSpaceId?, query? }` に固定する
  - `query` は条件と並べ替えだけ。`limit` / `offset` を含めば拒否し、長さは 500 文字まで。サーバーが末尾に固定の `limit 5` を付ける（AI は件数を変えられない）
  - 返すのは 1 件ごとの形の要約だけ: `$id`、文字列の文字数・行数、数値の桁、テーブルの行数、添付の件数と種類。値・ファイル名・ユーザー名は返さない（今の `record --summary` と同じ考え）
  - 応答の大きさに上限（例 64 KB）を付け、超えたら打ち切って `findings` に出す（kSQL はレコードにバイト数の上限が無かったので足す）
  - 値が要るとき（preview の入力）は `pcraft_record` で作業フォルダーに保存する（値は AI に返さない）
- **kintone から受け取る量にも上限を付ける**（AI に返す量の上限とは別）。今の `kintone-rest.ts` は `res.text()` で本文を全部読んでから JSON にしている。`app` と `records` の応答に固定の上限（例 2 MiB。kSQL の B49 と同じ）を付け、`Content-Length` が上限を超えれば本文を読まずに拒否し、`Content-Length` が無い・偽りでも、読みながら上限 + 1 バイトで止める。JSON にするのは上限の確認の後だけ
- 許可する API（`tools/src/kintone-rest.ts` の `ALLOWED_APIS`）に足すのは `records` だけ。GET だけ、送信先の検証、URL・メソッド・本文を AI から受け取らない、は今のまま
- API ごとの認証方式・入力・受け取る量と AI に返す量の上限は [api-table.md](api-table.md)（0-1 ②）。**`pull` が使うプラグインの設定情報の API（API ラボ）は、資料の API トークンで使える API の一覧に載っていないが、閲覧だけの API トークンで運用環境の設定を取れた**（2026-10-09 試作 0-4。動作テスト環境はアプリ管理の権限が要り 403）。Desktop の `pcraft_pull` は運用環境だけを出す。API ラボが無効な環境などで失敗したら、ダウンロード → `inbox/` → `pcraft_take` を案内する

### 5.5 手順と資料（`instructions` と `pcraft_docs`）

- **Desktop のチャットには、ツールしか届かない。** kSQL の B55: Desktop は手元の MCP サーバーを中継（`remote-devices`）して、ツールだけを届け、resources と prompts は届かなかった。**試作 0-4（2026-10-09）で、サーバーの指示（`instructions`）も AI に渡らないと分かった**（5b: AI に見える MCP の指示は Claude in Chrome のものだけ）。さらにツールは遅れて読み込まれ、AI には最初**名前だけ**が見える。資料は**ツール**で渡し、AI を導くのは**ツールの名前と説明**
- **ツールの名前**: Desktop では `mcp__claude-device__lcl-<表示名の英数字の部分>-<ツール名>`（例 `mcp__claude-device__lcl-Print_craft-pcraft_docs`。空白は `_`）。表示名に英数字の識別しやすい名前（`Print craft`）を入れる。名前の長さの上限（64 文字と見られるが未確認）を超えないよう、英数字の部分とツール名は短く保つ
- **ツールの説明**: 利用者の言葉（印刷屋、帳票、見積書・請求書の PDF、印刷屋の設定）と「最初に呼ぶ」を `pcraft_docs` の説明に書く。試作 0-4 の 0.0.3 で、あいまいな「印刷屋の設定を作って」でも結び付いた（0.0.2 の説明では結び付かなかった）。印刷屋の言葉が無い「見積書の帳票を作りたい」は結び付かない（Excel などと区別できない）ので、利用者には「印刷屋で〜」と頼んでもらう（README・使い方の例）
- **`pcraft_docs`**: 引数なしで目次（版の行で始め、作業の順・禁止事項・「状態は手順の文から推し量らず `pcraft_status` / `pcraft_workspace_status` で確かめる」を書く。AI は setup の手順の文から「未設定」と推し量った。試作 0-4 の 5d）、`section` でその章の文章、知らない `section` は正しい名前の一覧を付けてエラー。読み取りだけ、文章だけ。中身はスキルと同じ元（テンプレートの `docs/`）からビルドのときに埋め込む
- **`instructions`**（初期化のときにサーバーが渡す指示。**Claude Code では届く見込み、Desktop のチャットでは届かない**。同じ要点を `pcraft_docs` の目次にも書く）: 1 行目に版、作業の順、禁止事項、ツールの一覧、「資料は `pcraft_docs` で読む」、実際の失敗から学んだ書き方の決まり（例: `${式}` は `ESC_HTML`、計算式の文字列に `//` を書かない）。短く保ち、語数を試験で固定する（kSQL の B81: 上限は「見直しのきっかけ」で、外の根拠は無い。固定はずれの検出に使う）
- resources は付けてもよいが、頼らない
- 版の確かめ方（kSQL の B101）: 更新の後も古いプロセスが動き続けることがある。`instructions` の 1 行目と `pcraft_docs` の目次の先頭に「この呼び出しに答えたサーバーの版」を出す。README に「更新したら Desktop を再起動し、新しい会話を始める」と書く

## 6. 接続情報（`.env`）を設定項目にする

**2026-10-10: kintone の接続（6.1 の `kintoneBaseUrl` / `kintoneApiToken` / `kintoneUsername` / `kintonePassword`、6.4 の `environments.json` の `envFile`）は 15 章（接続のファイル。kSQL と同じ形）で変えた。** 作業フォルダーと `pluginZip` は今のまま。

### 6.1 設定項目

| 今の `.env` の変数 | Desktop（`.mcpb` の `user_config`） | Claude Code（プラグインの `userConfig`） |
| --- | --- | --- |
| `KINTONE_BASE_URL` | `kintoneBaseUrl`（文字列、必須） | `kintoneBaseUrl` |
| `KINTONE_API_TOKEN` | `kintoneApiToken`（`sensitive`、必須） | `kintoneApiToken`（秘密） |
| `KINTONE_USERNAME` / `KINTONE_PASSWORD` | 最初の版は無し（API トークンだけ） | `kintoneUsername` / `kintonePassword`（秘密） |
| `PCRAFT_PLUGIN_ZIP` | `pluginZip`（`type: "file"`、必須） | `pluginZip`（絶対パス） |
| （新規） | `workspaceDir`（`type: "directory"`、必須。4.1） | `workspaceRoots`（文字列の配列。4.1） |

- MCPB の `user_config` の種類は `string` / `number` / `boolean` / `directory` / `file`、`sensitive` は文字列に付けられる（MCPB Manifest Spec）。**kSQL は `sensitive` を使っておらず前例が無い**（kSQL はトークンを OS の環境変数の参照で渡した。Windows は利用者の環境変数に置いて Desktop を完全に再起動する必要があった）。0-4 で必ず試す。公開の報告に、Desktop で `mcp_config.env` が子のプロセスに渡らないもの（[MCPB issue #297](https://github.com/modelcontextprotocol/mcpb/issues/297)。報告は binary の形のサーバーで、Node の形は未確認）と、`sensitive` の値がインストール後の設定画面で平文で見えるもの（[MCPB issue #244](https://github.com/modelcontextprotocol/mcpb/issues/244)）がある（どちらもこの文書では確かめていない）。だめなとき kSQL と同じ OS の環境変数の参照に戻すと、「`.mcpb` 1 つで設定画面だけで使える」目的を満たさないので、B3 に進むかの判断の条件にする（9 章の 0-4）
- プラグインの `userConfig` は `settings.json` の `pluginConfigs.print-craft.options` に、秘密の値は Claude Code の secure storage に入る（型定義の説明による）。OS の具体的な保管先、バックアップ、削除、ログへの出方は未確認。`register(on, options)` には平文で渡るので、フックの中で表示・記録しない
- Claude Code の `userConfig` はすべて任意にする（必須にすると値が無いときプラグインの読み込みが止まる）。無いときは `session.start` で知らせる

### 6.2 値の渡し方

| 渡し方 | 渡る先 | 評価 |
| --- | --- | --- |
| `.mcpb` の manifest の `mcp_config.env`（`"KINTONE_API_TOKEN": "${user_config.kintoneApiToken}"`） | Desktop の print-craft MCP | **採用（Mac で確かめた。2026-10-09 試作 0-4）**: Node の形で環境変数が届き（MCPB issue #297 の現象は出なかった）、引数・応答・標準エラーに出ず、インストール後の設定画面で平文にならなかった（issue #244 の現象も出なかった）。Windows と、ログの文字列での検索は残り（0-4 の項目 8・11） |
| プラグインの `.mcp.json` の `env`（`${user_config.*}`） | Claude Code の print-craft MCP | **採用**。公式の資料で Claude Code は値を聞いて渡す（Cowork は既定値が無いと無視、チャットは無視） |
| `$.env.set` | Claude Code の環境。以後の Bash、MCP サーバーがすべて受け継ぐ | 不採用。AI が `echo $KINTONE_PASSWORD` で見られる |
| コマンドが `.env` を書く | ファイル | 不採用。平文が残る |

秘密の値をチャットで聞かない（AI と会話の記録に渡る）。入力はインストールの画面か `/config` だけ。print-craft MCP は秘密の値を応答に入れない（5.2）。

### 6.3 kintone MCP

- **不採用: kintone MCP をプラグインの `.mcp.json` に移す**

- **Desktop で採用: print-craft MCP に要る GET を入れる** — `.mcpb`（5.4）

**2026-10-09 Takashi 決定。**（以前の版と 14 章では、順に A / B / C と呼んでいた） Desktop のチャットには `.claude/settings.json` の拒否の仕組みが無く、公式の kintone MCP を入れると書き込みのツールも使える状態になる。print-craft MCP の GET なら書き込みのツールがそもそも無く、利用者が入れるものも `.mcpb` 1 つ、トークンも 1 か所になる。kSQL も公式の kintone MCP の代わりではなく補う位置付けで、GET は決まった種類だけにしている。

### 6.4 tools（共通の中核）の変更

- 共通の中核は作業フォルダーと認証情報を**引数で**受け取る（`process.cwd()` と `process.env` に頼らない。12.3）。print-craft MCP は設定項目から受け取った値を渡す
- **`environments.json` があるとき、kintone の認証（`loadAuthForEnv`）は OS の `KINTONE_*` / `KSQL_*` を読まない**（`envFile` だけから読む。開発と本番の取り違えを防ぐため、2026-10-05 の設計）。ただし `PCRAFT_PLUGIN_ZIP`（`pluginZipPath`）と、アプリのフォルダーの外の設定を normalize / preview するときの接続先（`cli.ts` の 250 行目付近）は、そのときも OS の環境変数を読む
- 設定項目の接続先は「`environments.json` が無いときの接続先」とする。`environments.json` があるときは今のまま `envFile` から読み、print-craft MCP は kintone の認証の値を中核に渡さない。`pluginZip` は渡す
- **2 環境の秘密の値は最初の版で扱わない**（2026-10-09 Takashi 決定。README に制限として書く）。2 環境の利用者は Claude Code とテンプレートの `.env` / `env/` のまま。対応するときは、`environments.json` には秘密でない識別子（`credentialProfile`）だけを置き、資格情報はプロファイルごとに secure storage へ分ける。保存の鍵は「プラグイン + 作業フォルダーの実際のパス + `credentialProfile`」。プロファイルの名前・接続先・`role` が合わなければ拒否する。本番は閲覧専用の API トークンを原則にする
- `picker` が値の出所を返すようにする（`{ value, source: "process" | "file", file? }`）。`file` から来た値だけそのファイルのフォルダーから相対で解決し、`process`（設定項目）から来た値は `path.isAbsolute` でなければ止める。Windows のドライブ・UNC、macOS の絶対パスを試験する
- `.env` が無いときの文言を、設定項目も案内するように変える

### 8.3 作り方と検査（kSQL を写す）

- **MCP の SDK** — kSQL と同じく SDK v2（`@modelcontextprotocol/server`。kSQL の B99）で作る。Desktop はプロトコルの新旧を試し（`server/discover`）、手書きの試作は「legacy」、kSQL は「modern」と判定された（試作 0-4 のログ）
- **ビルド** — esbuild で core と依存を 1 つの CJS ファイルにまとめる（`bundle: true`、`platform: node`、`target: node20`）。ビルドの後に外部の `require("@modelcontextprotocol/…")` や `require("zod")` が残っていれば失敗にする（kSQL の `build-mcp.mjs`）

- **manifest** — `package.json` から作る（`name`、`version`、`display_name`、`server.type: "node"`、`entry_point`、`mcp_config`、`user_config`、`compatibility`: `platforms ["darwin","win32"]`、`runtimes.node ">=20.0.0"`）。kSQL は独自の zip の書き出し（`build-mcpb.mjs`）で `@anthropic-ai/mcpb` の CLI を使っていない。どちらでもよい
- **検査**（kSQL の `mcpb-verify.mjs`）— `.mcpb` を開き、要るファイル、manifest の値（版が `package.json` と同じ、`user_config` の種類と必須）、ツールの一覧、起動のファイルを確かめる。展開して本物の MCP のクライアントで起動し、`instructions` の語、`listTools`、`pcraft_docs` の応答、ツール 1 つの呼び出しを確かめる。`.gitignore` に出力先があることも確かめる
- **署名** — kSQL はしていない。Desktop での扱いは未確認

   - 対策: 拒否するときの文で「print-craft MCP の保存のツール（`pcraft_save_settings` / `pcraft_update_button`）を使う」と案内する。README に「プラグインを入れるときはテンプレートも更新する」と書く。互換表の参考の値（`cliVersion`。7 章）でテンプレートの組み合わせを示す
4. **細かい変更**
   - `PCRAFT_PLUGIN_ZIP` を OS の環境変数に**相対パス**で書いている人はエラーになる（6.4。`.env` に相対パスで書くのは今のまま）。エラーの文で絶対パスにするよう案内する
   - kintone から受け取る量の上限（5.4）は、中核に入れると CLI の `fields` などにも効く。上限は API ごとに決め、大きなアプリの項目定義・レイアウト・プラグインの設定（data: の URL を含み保存値は 256 KB まで）で引っかからない値にする（0-1 の API の表）

## 13. 一般の Claude ユーザー向け（Claude Desktop）

### 13.1 Claude Code だけの形の限界

Claude Code のプラグインは入れるのは簡単だが、Node.js と `npm ci`（kintone MCP）、テンプレートを clone した作業フォルダー、開発者向けの画面が要り、一般の利用者には重い。Claude Desktop のコードの画面から入れても同じ。

### 13.2 一般の利用者の形: Claude Desktop のチャット + `.mcpb` 1 つ

公式の資料で確かめた、プラグインが画面ごとに読み込むもの:

| プラグインの中身 | チャット（web・Desktop・スマホ） | Cowork（Desktop） | Claude Code |
| --- | --- | --- | --- |
| スキル | 読む | 読む | 読む |
| フック | 無視 | 読む | 読む |
| 手元で動く MCP（プラグインの中の `.mcpb` も） | **無視** | Cowork のセッションが手元の PC で動くときだけ | 読む |
| `${user_config.*}` を使う MCP の設定 | 無視 | 既定値が無い項目があると無視（値を聞かない） | 読む（値を聞く） |

**チャットではプラグインの print-craft MCP が動かない**ので、チャットで使うには `.mcpb` を Desktop の拡張機能として入れる（Settings > Extensions。プラグインとは別の入れ方）。

一般の利用者に勧める形:

| 入れるもの | 入れ方 | 役割 |
| --- | --- | --- |
| **print-craft の `.mcpb`**（必須） | GitHub のリリースからダウンロードしてダブルクリック | print-craft MCP（`--surface desktop`）。kintone の GET（5.4）、項目・レコードの保存と要約、設定の保存（normalize を通ったときだけ）、preview、手順と資料（`pcraft_docs`）。Desktop（macOS、Windows）が Node を同梱しているので、利用者は Node を入れなくてよい |
| `.mcpb` の設定項目 | インストールの画面 | kintone の URL、API トークン、印刷屋の zip（ファイルを選ぶ画面）、作業フォルダー（フォルダーを選ぶ画面）。6.1 |
| print-craft のプラグイン（任意） | Customize > Plugins > Add marketplace | Cowork と Claude Code を使う人向け。チャットではスキルだけが効く |

- 手順と資料は `pcraft_docs`（5.5）で渡す。Desktop のチャットには `instructions`・resources・prompts が届かない。**`.mcpb` 1 つで配るのを基本にする**（2026-10-09 試作 0-4: ツールの名前と説明で、あいまいな「印刷屋の設定を作って」でも AI が `pcraft_docs` などを呼んだ）。手順のプラグイン（Customize）は任意。保存のツールまで正しく呼べるかは、B1 の print-craft MCP で確かめる
- 利用者には「印刷屋で見積書の帳票を作って」のように**印刷屋の言葉を入れて頼んでもらう**（印刷屋の言葉が無いと、Excel のひな形などと区別できず結び付かない。README と使い方の例に書く）
- 公式の kintone MCP は Desktop では入れない（6.3）

**初めの準備（1 回だけ）**

1. Claude Desktop（Mac か Windows）を入れてログインする
2. 印刷屋プラグインの zip を用意する（アプリに入れているものと同じ版。配布元から入手したもの）
3. kintone で、対象のアプリの「レコード閲覧」だけの API トークンを作る
4. 作業用のフォルダーを 1 つ作る
5. print-craft の `.mcpb` を入れ、インストールの画面で URL、トークン、zip、作業フォルダーを入れる

**毎回の使い方**

1. Desktop のチャットで、アプリの番号か URL を添えて頼む（例「アプリ 3740 の見積書を作って。明細はテーブル、合計は右下、社印を入れて」。アプリの名前だけでは探せない。5.4）
2. Claude が項目とレコードの形を見て、ラベルとフィールドコードの対応を示す。違えばチャットで直してもらう
3. Claude が設定を作業フォルダーに保存する（normalize を通ったときだけ）。警告は説明される
4. 作業フォルダーの `out/…html` をブラウザーで開いて見た目を確かめる
5. kintone のアプリの設定 → 印刷屋プラグインの設定 → 設定をアップロード → 取り込み方を選ぶ → 保存する → 運用環境に反映
6. 詳細画面でボタンを押して PDF を確かめる

更新したときは Desktop を再起動し、新しい会話を始める（5.5）。

### 13.3 print-craft MCP が守ること

Desktop のチャットではフックが動かないので、制約は print-craft MCP の中で守らせる。**スキル・`pcraft_docs` は案内、print-craft MCP は強制の境界**。

- 既存の設定ファイルを丸ごと返さない（`pcraft_buttons` の形で返す。ボタン単位で取り出し・更新する）。新しい設定は AI が作るので、その内容が AI に渡ること自体は止めない。止めたいのは既存の設定の丸ごとの読み出し、大きな data URL、個人情報
- レコードの値を AI に返さない（`kintone_list_records` は形だけ、`pcraft_record` は保存して形だけ。5.4）
- 変えるのは作業フォルダーの中だけ（書くのは `fields/` `records/` `settings/` `temp/` `out/` `kintone/`、`take` は `inbox/` の元のファイルを消す）。作業フォルダーは 4.1 で決め、AI の引数では作業フォルダーの外に出られない
- **本番の環境は読み取り専用**（2026-10-09 Takashi 決定。**2026-10-10 Takashi: やめた。15 章。以下のこの項目は print-craft MCP には当てはまらない（CLI は B1 では今のまま）**）。`environments.json` の環境の `role`（`development` / `production`）で決める
  - `role: "production"` の環境のフォルダー（`kintone/<ホスト名>/<番号>-<アプリ名>/`）では、変更を伴う操作をすべて拒否する: 保存（`pcraft_save_settings` / `pcraft_update_button`）、`edit`、normalize の書き戻し、`fields` / `record` の書き込み、`pull --force`、アプリのフォルダーの `out/` への preview の出力（本番の preview は作業フォルダーの `out/` に出す）。許すのは `pull` と `take`（新しいファイル名で増やすだけ。既にある名前は書き換えない）、`buttons`、`files`、`diff`、normalize の `--dry-run` / `--check`（permission-table.md 4.2。0-2 の Codex 再々レビュー MINOR 5 で表に合わせた）
  - `role` は書くもの（`environments.example.json` とバージョンアップ手順で案内する）。JSON で許す値は `development` / `production` だけ（`"unclassified"` とは書けない）
  - **「未分類」**は内部だけの状態。`role` の無い環境と、`environments.json` の無い作業フォルダーの `kintone/<ホスト名>/<番号>-<アプリ名>/` は未分類として、読み取りと診断だけを許し、`kintone/` の下を変える操作をすべて拒否する（暗黙に開発とみなさない）。`environments.json` を消す・名前を変えることで本番の保護を外せないようにするため
  - 拒否するときは、環境の名前と「`environments.json` の環境に `role` を書く」という固定の文を返す。`pcraft_workspace_status` で、どの環境が未分類かを示す
  - `kintone/` の下を変える操作の直前に、`environments.json` の有無・digest・`role` を取り直す（起動のときに読んだ値を使い続けない）
  - `environments.json` の無い作業フォルダーの `settings/`、`fields/`、`records/` など（今の 1 環境の使い方）は今のまま
  - 未分類の扱いは移行のためのものとして残し続ける（期限は設けない。`role` を書けば解ける）。やめるときはバージョンアップ手順で知らせる
- ダウンロード / pull のファイルは変えない（編集は `-edit.json` だけ）、normalize のエラーが 0 になるまで確定しない（5.3）
- `policy/`、`.env`、`env/`、`environments.json` はツールの対象にしない
- kintone に書き込まない（GET だけ。今の tools と同じ）
- 秘密の値を AI に返さない（5.2）

### 13.4 課題

- **preview** — `out/*.html` は利用者にブラウザーで開いてもらう（今と同じ）
- **Cowork** — プラグインの print-craft MCP は Cowork で動くが、`${user_config.*}` の値を聞く画面が出ない（既定値が無いと MCP が無視される）。秘密の値の渡し方が決まるまで Cowork は対象外
- **kintone の GET の保守** — print-craft MCP に足した GET（`app`、`records`）は自分で保守する。帳票の作成に要る範囲だけなので影響は小さい
- **Node の版** — Desktop が同梱する Node の版は公開資料に書かれていない。manifest の `compatibility.runtimes` に `node >=20.0.0` を書き（kSQL と同じ）、macOS と Windows の両方で試す。tools の依存は `happy-dom`（JavaScript だけ）なので、OS ごとに作り分けなくてよい見込み
- **使える場所** — Claude Desktop（macOS、Windows）だけ。claude.ai のウェブ版とスマホでは使えない
- **既存の設定の取り込み** — 利用者がダウンロードした設定を作業フォルダーに置く手順（今の `inbox/` と `pcraft_take`）を、Desktop の利用者に分かる形で案内する
- **zip のコードの実行（受け入れた危険）** — 中核は zip の `SIGNATURE` を検証せず、`PUBKEY` から出るプラグイン ID だけを確かめて、zip のコードを利用者の権限で動かす（`tools/SECURITY.md`）。print-craft MCP では、そのコードが認証情報と同じプロセスで動く。**2026-10-09 Takashi 判断で今のまま**（14 章）。README、MCPB のインストールの説明、設定項目の zip の欄の説明に、同じ文で次を書く

  > 指定した印刷屋プラグインの zip の中のコードを、この PC の利用者の権限で動かします。zip の署名（SIGNATURE）は検証しないので、中身が改変されていても自動では見分けられません。そのコードは kintone の認証情報を扱うプロセスの中で動きます。zip は印刷屋プラグインの配布元から直接入手したものだけを指定し、他の人から受け取った zip は指定しないでください。
- **リモートの MCP サーバーとの比較** — リモートなら更新を中央で管理できるが、手元の zip と作業フォルダーに触れない。設定、項目定義、レコード（場合によっては zip）をサーバーに送る設計になり、データの保持、暗号化、テナントの分離、監査、利用規約、障害時の運用が要る。ローカルの MCP サーバーを第一の候補にし、リモートは別の製品の案として分ける
- Claude のディレクトリへの登録、MCPB の署名、プランごとに使えるかは、実機で確かめるまで採用の判断に使わない

## 15. 接続のファイル（kSQL と同じ形。2026-10-10 の設計変更）

B1 の手での確認で、利用者（Takashi）から「kintone の接続情報の設定がわかりにくく、1 ドメイン 1 アプリしか対応できない」「kSQL と同じにできるか」「kSQL MCP の設定と共有できるか」と出た。6 章（設定項目 1 組。`environments.json` の `envFile`）と 13.3（本番は `role` で読み取り専用）を、この章のとおりに変える。

### 15.1 決まったこと（2026-10-10 Takashi）

1. **kintone の接続は、kSQL の `ksql.config.json` と同じ形のファイル（以下「接続のファイル」）にする**。kSQL のファイルそのものを指しても、別のファイルでもよい
2. **アプリは番号で指定し（Desktop はアプリの URL も。5.4）、名前は kintone の API（アプリの情報）から取る**。`environments.json` の `apps`（名前と番号の対応）はやめる
3. **本番の保護（`role`）はやめる**（13.3 の「本番の環境は読み取り専用」を取り消す）
4. **アプリのフォルダーは `kintone/<profile>/<アプリ ID>-<アプリ名>/`**（`<ホスト名>` でなく profile の名前で分ける）
5. **B1 の中で、手での確認の前に入れる**。中核の変更は tools 1.4.0

この章に無いことは今のまま（作業フォルダーの照合 4.1、応答の形 5.2、保存の約束 5.3、kintone には GET だけ、レコードの値と秘密の値を AI に返さない、互換表 7 章）。

### 15.2 接続のファイル

kSQL の形（`kintone-sql-tools/src/node/config.ts` の `KsqlConfig`）のうち、次のキーだけを読む。ほかのキー（kSQL の `query`、`output`、`dml`、`logicalApps`、`allowPhysicalAppRefs`、`mcp` など）と知らないキーは読まずに通す（kSQL も知らないキーを無視する。2026-10-10 に `validateKsqlConfig` と kSQL MCP の読み込み `loadOptionalKsqlConfig` で確かめた）。

```json
{
  "defaultProfile": "dev",
  "profiles": {
    "dev": {
      "baseUrl": "https://dev-example.cybozu.com",
      "tokenMap": { "APP101": "env:PCRAFT_TOKEN_APP101", "APP102": "env:PCRAFT_TOKEN_APP102" }
    },
    "prod": {
      "baseUrl": "https://example.cybozu.com",
      "auth": "userpass",
      "username": "print-craft-reader",
      "passwordEnv": "PCRAFT_PROD_PASSWORD"
    },
    "guest": { "baseUrl": "https://example.cybozu.com", "guestSpaceId": 15, "tokenMap": { "APP300": "env:PCRAFT_TOKEN_APP300" } }
  }
}
```

| キー | 読み方 |
| --- | --- |
| `defaultProfile` | ツールが `profile` を省略したときの profile。無ければ、profile が 1 つだけのときはそれ、2 つ以上なら `profile` が要る（invalid） |
| `profiles.<名前>` | profile の名前は `^[A-Za-z0-9_-]{1,40}$`（フォルダーの名前になる）。合わない名前の profile は使えない（診断で名前だけ示す） |
| `baseUrl` | 中核の `normalizeKintoneBaseUrl`（`*.cybozu.com` / `*.kintone.com` / `*.cybozu.cn`、ユーザー情報・パス・ポート無し） |
| `guestSpaceId` | ゲストスペースの番号（ツールの `guestSpaceId` より優先しない。ツールで指定すればそれ、無ければ profile の値） |
| `auth` | `token` / `userpass` / `auto`（既定）。`auto` はログイン名とパスワードがそろえば `userpass`、無ければ `token`（kSQL と同じ） |
| `tokenMap` | アプリごとの API トークン。キーは `APP<番号>`（大文字小文字は問わない）か `<番号>` で、`APP<番号>` にそろえる（kSQL の `normalizeAppKey` と同じ）。それ以外のキーがあれば、その profile は使えない。値は `env:<変数名>`（その環境変数の値）か、トークンそのもの |
| `username` / `password` / `passwordEnv` | ログイン名とパスワード。パスワードは `passwordEnv`（環境変数の名前）が先、無ければ `password` |

- **kSQL の環境変数による上書き（`KSQL_BASE_URL`、`KSQL_TOKEN`、`KSQL_TOKEN_MAP`、`KSQL_USERNAME`、`KSQL_PASSWORD`、`KSQL_AUTH`、`KSQL_PROFILE`、`KSQL_GUEST_SPACE_ID`）は読まない**。すべての profile に効いてしまい、どの接続先の資格情報かが分からなくなるため（6.4 の「OS の `KINTONE_*` を読まない」と同じ考え）。読む環境変数は、ファイルが名前を書いたもの（`env:` と `passwordEnv`）だけ
- アプリ N の認証: `token` なら `tokenMap` の `APP<N>`。無ければ「profile『dev』の tokenMap に APP101 が無い」（invalid。値は出さない）。`userpass` ならログイン名とパスワード（どちらか無ければ invalid）
- `env:` の変数が無い・空なら「環境変数 PCRAFT_TOKEN_APP101 が無い」（failed。変数の名前は秘密でないので出す。値は出さない）。Desktop（Mac）は、シェルの設定（`~/.zshrc` など）の環境変数が Desktop に渡らない。Mac の Desktop では、トークンをファイルに直接書くか、`launchctl setenv` で置いて Desktop を起動し直す（README に書く。kSQL の手順は Windows の利用者の環境変数）
- 置き場所: **作業フォルダーの外**。実際のパス（symlink を解いたもの）が、登録済み・設定の作業フォルダーのどれかの中なら使わない（failed。AI が作業フォルダーのファイルとして読めないように）。絶対パスだけ（設定の値は `~/` を展開し、両端の引用符を外す。4.1 と同じ）。大きさは 256 KiB まで、UTF-8 の JSON
- 読むのはツールを呼ぶたび（小さいファイル。書き換えたら再接続なしで効く）。読めない・形が違うときは、ファイルの名前（パスでなく）と、どのキーが違うかだけを返す（中身・秘密の値を返さない）
- 秘密の値（トークン、パスワード、`env:` の値）は応答・findings・標準エラー・ファイルに出さない。診断に出すのは、profile の名前、ホスト、認証の種類、`tokenMap` のアプリの番号、`env:` の変数の名前とあるかないかだけ
- print-craft MCP は kintone に GET しか送らない（中核の REST の許可した API だけ）。kSQL で書き込みもする API トークンを共有しても、print-craft MCP からは書かない。それでも、print-craft 用には閲覧だけのトークンを勧める（README）

- **kintone の接続は接続のファイルだけ**（print-craft MCP は作業フォルダーの `.env` の `KINTONE_*` と `environments.json` の `envFile` を読まない）。入れる場所を 1 つにするため
- 接続のファイルが未設定なら、kintone を使うツール（`pcraft_fields`、`pcraft_record`、`pcraft_pull`、`kintone_*`）は failed（「設定の『kintone の接続のファイル』に ksql.config.json と同じ形のファイルを選ぶ」）。kintone を使わないツール（保存、normalize、preview、buttons、diff、files、take、edit）は動く
- Claude Code の公式の kintone MCP（テンプレートの `.mcp.json` と `.env`）は今のまま（6.3）

### 15.4 作業フォルダーの形

- アプリのフォルダーは **`kintone/<profile>/<アプリ ID>-<アプリ名>/`**。中身は今の `kintone/<ホスト名>/…` と同じ（`fields.json`、`records/<レコード番号>.json`、`out/`、ダウンロード / pull のファイル、`-edit.json`、新しい帳票）
- アプリ名は `pcraft_fields` / `pcraft_pull` が kintone の API（アプリの情報）から取る。番号のフォルダーが既にあれば、名前が変わってもそれを使う（今のまま）
- 同じドメインの profile が 2 つ（例: 開発用のアプリと本番のアプリ、ゲストスペース）でも、profile ごとにフォルダーが分かれる
- **print-craft MCP は `environments.json` を読まない**（`pcraft_workspace_status` は「あるが使わない（CLI の形）」とだけ示す）。CLI（テンプレート）は B1 では今のまま `environments.json` と `.env` を使う（15.8）
- `settings/` `temp/` `fields/` `records/` `out/` は今のまま使える（AI が保存した設定、項目定義のパスを明示した normalize / preview）。kintone から取るツール（`pcraft_fields`、`pcraft_record`、`pcraft_pull`）の保存先は、いつもアプリのフォルダー

### 15.5 書ける場所と守り（本番の保護をやめた後）

| 場所 | 変える操作 |
| --- | --- |
| `settings/` `temp/` `out/` | 今のまま（保存、差し替え、preview の出力） |
| `kintone/<profile>/<アプリ>/`（`<profile>` が接続のファイルにある） | すべて許す: 保存、差し替え、`edit`、`fields`、`record`、preview の出力、`pull` と `take`（新しい名前で増やす） |
| `kintone/<名前>/`（`<名前>` が接続のファイルに無い） | 拒否（denied。「接続のファイルに profile が無い」）。読み取りと一覧はする |
| ダウンロード / pull のファイル（`rex0220-print-craft-app<番号>-<日時>.json`） | どこでも書き換えない（直すのは `-edit.json`。今のまま） |

- 本番だけを読み取り専用にする守りは無い。本番の設定を見るだけなら、閲覧だけのトークンを勧める（print-craft MCP は kintone に書かないので、kintone の本番は変わらない。変わりうるのは作業フォルダーの中のファイルだけ）
- `kintone/` の下を変える直前に、接続のファイルを読み直して profile があるかを確かめる（起動のときに読んだ値を使い続けない）

### 15.6 ツールの変更

| ツール | 変更 |
| --- | --- |
| `pcraft_fields` / `pcraft_record` / `pcraft_pull` | `env` → `profile`（省略は `defaultProfile`）。`app` は番号だけ（名前はやめる）。保存先は `kintone/<profile>/<アプリ>/`。認証はその profile のそのアプリ（15.2） |
| `kintone_get_app` / `kintone_list_records`（Desktop） | `env` → `profile`。アプリの URL は、そのオリジンが profile の `baseUrl` と同じときだけ（5.4） |
| `pcraft_files` | `env` → `profile`。`app` を付ければそのアプリのフォルダー、無ければ profile ごとのアプリのフォルダーの一覧と `settings/` など |
| `pcraft_take` | 行き先の profile: `profile` を付ければそれ。無ければ、封筒の `appId` を `tokenMap` に持つ profile が 1 つだけならそれ、profile が 1 つだけならそれ。決まらなければ移さず理由を返す（「どの profile のアプリか決まらない。profile を付ける」） |
| `pcraft_edit` | `env` → `profile` |
| `pcraft_workspace_status` | `environments.json` の代わりに接続のファイル: 設定されているか、読めるか、`defaultProfile`、profile ごとに名前・ホスト・認証の種類・`tokenMap` のアプリの番号・`env:` の変数があるか。ファイルが作業フォルダーの中なら問題として示す |
| `pcraft_status` | 接続のファイル: 設定されているか（ファイルの名前だけ）、読めるか、profile の数 |
| preview の iframe の接続先（`trustedBaseUrl`） | アプリのフォルダーの設定は、その profile の `baseUrl`。それ以外（`settings/` など）は `defaultProfile` の `baseUrl`（無ければ iframe を使わない） |

### 15.7 中核（tools 1.4.0）の変更

- 新しい `src/connections.ts`: 接続のファイルを読む（15.2 の形・制限・作業フォルダーの外か）、profile を選ぶ、アプリ N の認証（`KintoneAuth`）を作る。誤りは `ConnectionError`（`code`: `not-configured` / `unreadable` / `inside-workspace` / `no-profile` / `profile-invalid` / `no-token` / `env-missing` / `no-userpass`）。中核の入口 `/core` に足す（足すだけなので `CORE_API_VERSION` は 1 のまま）
- アプリのフォルダー: `appDirFor` / `findAppDir` / `appFolderOfFile` / `listAppFolder` に「profile で分ける形」を足す（`kintone/<profile>/…`。今の `kintone/<ホスト名>/…` は CLI のために残す）
- 許可（`permission.ts`）: 「profile の形」を足す。`kintone/<profile>/` は profile が接続のファイルにあれば変えてよい、ダウンロード / pull のファイルは書き換えない。`role` は見ない。保存（`save.ts`）・`take`・`pull` は、どちらの形かを引数で受け取る（print-craft MCP は profile の形、CLI は今の形）
- CLI は B1 では変えない（`environments.json`、`--env`、`.env`）。CLI を接続のファイルに移すか（`--profile`）、`environments.json` の形を残すかは B2 でテンプレートの文書と一緒に決める（15.9）

### 15.10 試験

- 接続のファイル: kSQL の README・手順書の例をそのまま読める、知らないキーを通す、`defaultProfile` の決め方、profile の名前の制限、`tokenMap` のキーの形（`APP101`、`app101`、`101`、不正なキー）、`auth` の 3 通り、`passwordEnv` と `password`、`env:` の変数が無い・空、kSQL の環境変数の上書きを読まない、作業フォルダーの中にあるファイル（symlink を含む）を断る、大きすぎる・JSON でない
- 秘密の値が応答・findings・標準エラー・作業フォルダーのファイルに出ない（偽の kintone で、送ったヘッダーのトークンがアプリごとに正しいことも確かめる）
- フォルダー: `kintone/<profile>/<番号>-<名前>/`、名前が変わっても番号で探す、接続のファイルに無い profile のフォルダーへの書き込みを断る、ダウンロード / pull のファイルを書き換えない
- `take` の行き先の決め方、`pcraft_files` / `pcraft_edit` / `pcraft_pull` の profile、Desktop の `kintone_*` の URL と profile のオリジン
- 接続のファイルが未設定のとき、kintone を使わないツールは動き、使うツールは failed
